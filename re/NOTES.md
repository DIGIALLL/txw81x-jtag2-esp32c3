# Разбор CK-Link Lite 2.36 (STM32F103), протокол JTAG2/CKHAD

Файл: `cklink-lite-fw-convertor/cklink_lite-2.36_for-stm32f103.hex` → `fw.bin` (база 0x08000000).
Инструменты: `scan.py` (поиск ссылок на GPIO), `dis.py <addr> <len>` (capstone, Thumb).

## Выводы STM32
- PA1 = TCK  → bit-band ODR: 0x42210184
- PA5 = TMS/данные (двунаправленный в 2-wire) → bit-band ODR: 0x42210194, чтение GPIOA_IDR бит 5
- PA7 = вероятно управление направлением буфера (BSRR/BRR 0x80 в 0x80086c0/0x80086ec)

## Примитивы
- `0x080060f4` — один такт: TCK=0, nop, TCK=1 (данные защёлкиваются по фронту вверх).
- `0x080086c0` — PA5 → вход (GPIO_Init mode 0x48, input pull-up), PA7=1.
- `0x080086ec` — PA5 → выход (GPIO_Init mode 0x10, push-pull), PA7=0.
- `0x08004940` — GPIO_Init(port, cfg).

## Чтение байта (0x080061c8…)
- 8 бит, младшим вперёд: такт → чтение PA5 после фронта → `r7 = (r7>>1) | (bit<<7)`.
- Между байтами линия данных переключается вход/выход (вокруг такта turnaround).

## Таблицы драйверов (3 набора, выбор по режиму)
- 0x800a3a0..0x800a3c8 — **JTAG2 (родной 2-wire C-SKY)**: IR=0x800840c, DRwrite=0x8008088, DRread=0x8007e00,
  scan(IR+DR)=0x8007d70; медленные варианты 0x8008554/0x80082a0/0x8007f64/0x8007d98.
- 0x800a3cc..0x800a3f8 — cJTAG/OScan1-подобный (3 такта на бит: ~TDI, TMS, TDO-слот), IR 0x8006720/0x80068b8,
  DR 0x8006168/0x80063b8 — для других целей, нам скорее не нужен.

## Кадр JTAG2 (бит выставляется на HDA, затем такт HCK 0→1; всё младшим битом вперёд)
| Кадр | Заголовок (5 бит) | Далее |
|---|---|---|
| IR write | 0 0 0 1 1 | N бит IR, parity, 1, 1, +1 такт (d=1), idle |
| DR write | 0 0 1 1 1 | данные (дополняются нулями до ≥32 бит, если флаг=0), parity, 1, 1, +1 такт, idle |
| DR read  | 0 1 1 1 1 | HDA→вход, 1 такт (TRN), N бит данных (сэмпл после фронта), 2 такта (parity+TRN), HDA→выход, d=1, 2 такта, idle |

- Похоже: бит0=START(0), бит1=R/W (1=read), бит2=RS (0=IR,1=DR), биты3-4 = 1 1.
- parity = NOT(XOR всех бит данных) (нечётная).
- idle (0x80083b8): несколько тактов с HDA=1, число из конфигурации.
- Сэмпл данных при чтении: после фронта TCK вверх читать HDA.

## Регистры HAD (из T-HeadDebugServer Target.dll, таблица @0x334350, шаг 0xb0)
IR = HACR (8 бит). Предположительно как у M*Core OnCE: bit7 R/W (1=чтение), bit6 GO, bit5 EX, bits4..0 RS.
| RS | имя | | RS | имя |
|---|---|---|---|---|
| 0x02 | HID (ID модуля HAD) | | 0x11 | WBBR |
| 0x03 | HTCR | | 0x12 | HAD_PSR |
| 0x04/05 | MBCA/MBCB | | 0x13 | HAD_PC |
| 0x06 | PCFIFO | | 0x14 | IR |
| 0x07/08 | BABA/BABB | | 0x15 | CSR |
| 0x09/0a | BAMA/BAMB | | 0x16 | DCCDATA |
| 0x0b | CPUCSR | | 0x17 | ITMDATA |
| 0x0c | BYPASS | | 0x18 | **DDCADDR** |
| 0x0d | HCR | | 0x19 | **DDCDATA** |
| 0x0e | HSR | | 0x1a | CPUSEL |
| 0x0f | EHSR | | 0x1b | CPUST |
| 0x1e | BSEL | | 0x1f | HCDI |
| 0x20/21 | BABC/BAMC (банк 1) | | | |

- DDCADDR/DDCDATA — прямой доступ к памяти через HAD: записать адрес в DDCADDR, затем читать/писать DDCDATA.
  Код прошивки камеры исполняется с адресов 0x1802xxxx → флеш отображён (XIP) с 0x18000000 → дамп можно читать прямо через DDC.
- Строки DebugServer: "Read HID get 0x%x, HAD version is HAD_V%d", "Can not access to HAD module as DDCADDR can not be written".

## ПРОВЕРЕНО НА ЖЕЛЕЗЕ (2026-11-09, чёрная плата STD-X5-817-V02)
- Проводка: HCK=GPIO7, HDA=GPIO5 (C3 SuperMini). RST-пада не сбрасывает чип. Лог: TX камеры -> GPIO20 @115200.
- HID = 0x14039322. Протокол работает и на работающей камере (ловить загрузку не нужно).
- DR всегда 32 бита с дополнением (16-битное чтение без дополнения сбивает линию -> нужен lineReset).
- Вход в отладку: HCR = 0x8000 (DR). HSR&3==2 -> debug. HCR по умолчанию 0x4000.
- **Перед запуском HCR = 0x4000 (снять DR), иначе пошаговый режим** (биты HCR 2,3,13,15 = step).
- **CSR bit7 (0x80) = bkpt входит в отладку.** Без него bkpt -> исключение 7 (PSR.VEC=7) -> обработчик в ROM 0x1b9x.
- Выполнение инструкции: [CSR], IR write 0x54 (GO|IR), DR = (insn16<<16) | CSR. Выход: 0x74 (GO|EX|IR), insn = nop 0x6c03, PC через HAD_PC (0x13).
- Регистр rN <-> WBBR: CSR' = csr|0x80, hi=(hi&0xfe)|6|(wr), insn mov16 rN,rN; результат в WBBR (0x11/0x91).
- ld16.w r2,(r1)=0x9140, st16.w r2,(r1)=0xb140, addi16 r1,4=0x2103, movi16 r3,imm=0x33xx, bkpt16=0x0000.
- Флеш: XIP 0x18000000 читается ДАННЫМИ как 0xFFFFFFFF (только I-fetch); 0x08000000 не отображён.
  Читаем алгоритмом Taixin_TXW81X_FLASH_ALGORITHM.elf (FlashTools): грузится в 0x20000000,
  flashInit()=0x200001b0, flashID(&id)=0x200001d8, flashRead(ramBuf, flashAddr, len)=0x200001f0,
  g_rwBuffer=0x200011c8 (4 КБ). Вызов: r0..r2, r14=0x20040000, r15=0x20003000 (bkpt), PC=fn.
- **CSR биты 7,8 залипают после запуска кода** (CSR=0x180). Бит 7 = «операнд из WBBR»: если не снять,
  ld/st/addi работают не с регистрами -> буфер ОЗУ заполняется мусором, быстрое чтение повторяет 1-е слово.
  Для обычных операций всегда брать CSR & 0xfe7f; бит 7 ставить только на время запуска (bkpt -> debug).
- **Не взводить HCR.DR, если CPU уже в отладке** — запрос «запоминается» и срывает следующий запуск.
- **flashErase/flashChipErase только подают команду** (возврат 2–6 мс) — после них spiflash_wait_busy()
  (0x20000904) + пауза + проверка, что блок FF. Запись: по 4 КБ, проверка пустоты, буфера, чтение назад.
- USB C3: длинные ответы с сериями 'f' обрезаются -> ответ rblkf маскируется XOR (0x9E3779B9*(i+1)) + сумма,
  чтение по 64 слова. Serial.flush() на HWCDC может зависнуть — не использовать.
- Flash ID = 0xCD1460CD (1 МБ). Скорость чтения ~4 КБ/с (halfUs=0, GPIO через регистры).

## План первой проверки на железе
1. Сброс линии (~несколько десятков тактов с HDA=1).
2. IR write HACR=0x82 (read HID), DR read 32 бит → ожидаем не 0x00000000/0xFFFFFFFF.
3. Write DDCADDR=0x18000000, read DDCDATA → первые байты флеша (сравнить с заголовком образа).
